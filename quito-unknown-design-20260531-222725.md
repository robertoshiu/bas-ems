## Problem Statement

Build a **purely static, client-side** web app that convincingly impersonates a
semiconductor fab's **Building Automation System (BAS)** and **Energy Management
System (EMS)** — the facilities brain of the plant — in the visual and functional
language of Schneider EcoStruxure, Honeywell Forge/Niagara, and Johnson Controls
Metasys/OpenBlue. No backend, no auth, no server state. It runs from any static
host or directly from `file://`, animates continuously, generates all of its own
data from hash-seeded pseudo-randomness, plays ~3 minutes of non-repeating dynamic
content, then loops cleanly with no visible seam.

## Audience & Success Bar

**Audience:** fab facilities & energy engineers, and the execs who decide on a
BAS/EMS purchase. **The bar: a domain expert cannot immediately tell it is fake.**
Vocabulary must be correct, numbers must stay self-consistent, and — the decisive
test — **production activity must visibly drive facility load.** A demo built to
this bar automatically satisfies the easier "booth / marketing loop" bar.

## Premises (confirmed in session, D2)

- **P1 — Believability lives in the coupling, not the gauges.** Smart-factory

## Smart-Factory Event Model (the spine)

Authored against real fab automation standards so the stream survives expert review:

- **SECS/GEM collection events** (SEMI E5 SECS-II, E30 GEM, E37 HSMS) — each is a
  numbered **CEID** reported via **S6F11**, distinct from its human label: `LotStart`
  / `LotComplete`, `ProcessJobStart` / `ProcessJobEnd` (E40), `ControlJobStart` /
  `Complete` (E94), `CarrierID` read / `CarrierIn` / `CarrierOut` (E87),
  `SubstrateProcessed` (E90), `RecipeSelected` / `PPChanged`, `ProcessStart` /
  `ProcessComplete`, `ControlStateChange`, `LoadPortDock` / `Undock` (E84 handoff).
- **Alarms are a separate channel:** **S5F1 / S5F2** messages carrying `ALID` + `ALCD`
  (set / clear), *not* CEIDs — modeled distinctly so the tag-detail view is correct.
- **SEMI E10 equipment states** (RAM): Productive · Standby · Engineering ·
  Scheduled Downtime · Unscheduled Downtime · Non-Scheduled — streamed as
  transitions per tool.
- **AMHS** (OHT / stocker, E88): OHT vehicle dispatch + move, FOUP/carrier
  store/retrieve, load-port deliver/retrieve.
- **APC / FDC** (E133 APC, run-to-run): FDC excursion, SPC out-of-control,
  R2R recipe adjustment.
- **OEE / EPT** (E79 OEE, E116 EPT): Availability × Performance × Quality, and
  Busy/Idle/Blocked time tracking, ticking live.

Each event carries realistic fields drawn by hashed selection from master data:
`ts`, `area` (Litho/Etch/Diffusion/Implant/CMP/Wet/Metro/Thin-Film), `tool`
(e.g., `LITHO-SCANNER-03`), `recipe`, `lotId`, `carrierId`, and **either** a numeric
`CEID` (collection events, via S6F11) **or** `ALID` + `ALCD` (alarms, via S5F1),
plus the `loadVector` it imparts.

## Production → Facility Coupling Model

The believability engine. Each event type imparts a quantified `loadVector` onto
named facility systems with an exponential ramp then decay, layered on a periodic
baseline. Magnitudes are illustrative-but-plausible for a 300 mm advanced-logic fab,
tuned in QA against each system's baseline:

| Event type (area) | System | Δ (peak) | ramp τ | decay τ |
|---|---|---|---|---|
| Etch `ProcessJobStart` | Acid+solvent exhaust | +8–14% CFM | 6 s | 40 s |
| Etch `ProcessJobStart` | Abatement / scrubber | +60–120 kW | 8 s | 50 s |
| Etch process power | Tool RF power | +40–90 kW | 4 s | run-length |
| Diffusion furnace ramp | PCW tonnage | +20–40 RT | 30 s | 120 s |
| Diffusion furnace ramp | Electrical (heaters) | +150–300 kW | 25 s | run-length |
| Diffusion | N2 purge flow | +5–10% | 10 s | 60 s |
| Litho exposure | Scanner power | +15–30 kW | 3 s | run-length |
| Litho exposure | Cleanroom FFU / Δp | held tight (demand, not Δ) | — | — |
| Wet bench run | UPW draw | +30–60 m³/h | 5 s | 30 s |
| Wet bench run | Acid exhaust | +6–10% CFM | 5 s | 35 s |
| CMP run | UPW (slurry/rinse) | +25–50 m³/h | 5 s | 30 s |
| CMP run | PCW + vacuum/exhaust | +10–20 RT | 8 s | 45 s |
| Implant | HV electrical | +80–160 kW | 6 s | run-length |
| E10 → Standby/Idle | tool-driven loads | relax toward baseline | — | per-system τ |

**Loop-safe by construction (the key correctness rule):** `facilityLoad(t)` is a
**periodic sum over the deterministic event set of the entire 180 s loop**, using a
*wrapped* time distance `Δ = min(|t − tₑ|, 180 − |t − tₑ|)` for every event's
ramp/decay term. Because every tail is evaluated on the circle, a contribution still
decaying at t→180⁻ is identically present at t→0⁺ — **the seam is continuous by math,
not by crossfade.** Baseline analog signals are periodic functions of the clock for
the same reason. No crossfade is required; the hero canvas just renders `sim(t)` and
wraps with zero visible step.

## Deterministic Simulation Engine

- **Virtual fab clock:** the loop period is **exactly 180.000 s** of real demo time,
  representing **60 minutes of simulated fab time (20× compression)**. Time basis is
  **wall-clock-derived**: `t = ((performance.now() − t0) % 180000) / 1000`. Deriving
  `t` from wall-clock (not frame accumulation) makes the loop immune to RAF throttling
  when the tab is backgrounded — on return `t` is simply correct: no drift, no
  catch-up burst.
- **PRNG:** `xmur3(string) -> seed` then `mulberry32(seed) -> uniform`. For any
  `(channel, tick)` we hash `channel + ":" + tick` to a sub-seed → deterministic
  draw. This is the "hash-based pseudo-random combinations" requirement, reproducible.
- **Fixed tick grid:** event generation runs on an **exact 8 Hz grid = 1440 ticks per
  180 s loop** (`tick = floor(t * 8)`, range 0–1439). Render is RAF at display rate;
  analog values interpolate between ticks for smoothness. The *integer tick* is what
  the PRNG hashes, so the event sequence is bit-identical every loop.
- **Closed transitions per loop (seam rule for discrete state):** the generator
  guarantees every E10 state a tool *enters* within the loop also *exits* within it,
  and every `AlarmSet` has a matching `AlarmClear` before t=180. Equipment states and
  the alarm list are therefore identical at t=0 and t=180 — no step at the seam.
- **Frame state:** `sim(t) -> { events[], equipmentStates{}, load{}, kpis{},
  alarms[] }`, consumed by every module so all panels agree. All consumers read the
  same immutable frame object per render.

## Approaches Considered

### Approach A: Minimal viable
One/few-file, zero-dependency, DOM + CSS + light `<canvas>` for ticker/sparklines.
Fastest to ship, trivially portable, restrained visuals. Effort S–M, Risk Low.

### Approach B: Ideal architecture (CHOSEN)
Zero-dependency, modular classic-script files under a global namespace. Clean engine
core + DOM panels + **SVG system schematics** (chiller plant, UPW loop, gas yard) +
a **Canvas-2D "living fab" hero** that makes the production→load coupling visible.
No build step; runs from `file://`. Effort M–L, Risk Low–Med.

### Approach C: Creative / lateral
WebGL cinematic control-room (flowing pipes, moving OHT vehicles, bays lighting on
events). Maximum spectacle; highest effort/risk; 3D impresses laymen more than the
fab engineer who is the target. Effort L–XL, Risk Med–High.

## Recommended Approach — B now, C-hero later (D3)

Build **B** in full now: it clears the expert bar while honoring "purely static /
`file://`". Document **C's WebGL living-fab as a future upgrade** to the hero panel
once B is proven. Same starting code; the 3D escalation is a roadmap note, not a
rewrite.

### Feasibility resolution — the `file://` constraint

Modern Chrome/Firefox **block `type="module"` scripts loaded from `file://`** and
block `fetch()` of local files. To guarantee `file://` + offline works in every
browser:

- **No ES module `import`/`export` across files.** Use ordered classic `<script>`
  tags writing to a single global namespace (`window.BAS`).
- **No `fetch`.** All data is generated in-JS; nothing is loaded at runtime.
- **No web fonts over network.** System font stack (UI sans + monospace for
  readouts). Optional: a single base64-embedded display font if desired.
- **Optional single-file artifact:** a trivial concat step (or hand-assembled
  `bas-ems.html`) inlines all CSS/JS into one emailable HTML file. Pure convenience,
  not required to run.

## Modules (the believable-depth surface)

1. **Cleanroom Environmental** — per-bay temp / RH / **ISO 14644 particle class (tool
   bays ISO 3–5; generated counts must match the class, e.g. ISO 5 ≈ 3,520 particles
   ≥0.5 µm/m³)** / Δpressure (Pa), FFU bank airflow (m/s), MAU/AHU/RCU status, ULPA
   filter ΔP.
2. **Process & Chilled Water (PCW/CHW)** — chiller plant staging, supply/return
   temps, tonnage, approach, flow (m³/h), pump VFD %.
3. **Ultrapure Water (UPW)** — resistivity (target 18.2 MΩ·cm @25°C), TOC (ppb),
   flow, reclaim/reuse %, polish loop status.
4. **Bulk & Specialty Gas + Exhaust** — N2/H2/Ar/O2 bulk yard pressures + flow,
   gas cabinets/VMB status, scrubbers/abatement + thermal oxidizer load, exhaust
   headers (general/heat/acid/solvent/pyrophoric).
5. **Energy Command Center (EMS)** — total demand kW, kWh, kW/wafer, energy intensity
   (kWh/wafer, kWh/cm²·layer), facility-overhead ratio (facility ÷ process load — fab
   framing; the term "PUE" is never surfaced, since fabs have no IT-load denominator),
   demand peak, cost run-rate, sub-metered load by system.
6. **Sustainability** — CO2e, renewable %, water reuse % (foldable into #5 if scope
   tightens).
- **★ Production ↔ Facility correlation (hero)** — live smart-factory event ticker
  + the Canvas-2D living-fab showing events rippling into facility load.
- **🗂 Master data** — asset/equipment hierarchy (Site→Building→Floor→System→
  Equipment→Point), point/tag registry (BACnet/Modbus-style addressing), alarm/
  event log.

## Visual / Design System

Dark industrial SCADA. Generic-but-authentic, out-designing the references rather
than copying them. Tokenized: deep slate/near-black canvas, cyan/amber/green status
accents, red/amber alarm semantics, dense monospace readouts, thin grid lines,

escalation. No vendor logos/trademarks.

## Animation & Performance

- Single RAF loop drives all modules from one `sim(t)` frame; only the active view
  renders heavy visuals; off-screen modules update cheap KPIs.
- Canvas for high-frequency surfaces (ticker, sparklines, living-fab); SVG for
  schematics; CSS transitions for discrete state changes.
- **Zero per-frame allocation everywhere, not just the hero.** All time-series
  (sparklines, ticker, trend strips) use pre-allocated **ring buffers** — never
  `array.push/shift` (O(n) + GC churn that would violate the no-memory-growth
  criterion). Object pools for living-fab entities (OHT dots, pipe segments).
- **`file://` rendering caveat:** the living-fab draws only vector/primitive shapes;
  no `drawImage` from a `file://`-loaded `<img>` followed by `getImageData` (pixel
  readback is tainted/blocked under `file://`). Pure canvas primitives are unaffected.
- Budget: 60 fps on a mid-range laptop; flat memory across ≥30 min of looping.

## Master Data

Generated from seeded PRNG: ~8 process areas, ~40–80 tools with E10 state, a recipe
catalog per area, and the asset hierarchy — all stable across the loop. The point/tag
registry (≈30–60 points per tool/equipment, addressed like `AHU-12.SAT` /
`CHW.CHLR-03.kW`) is generated **lazily on demand** when a tool/asset is opened, so
boot stays light and memory stays flat. Events reference master data by hashed
selection.
